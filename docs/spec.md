# Спецификация начального прототипа sharetrip_notification

Статус: проект спецификации для реализации. Версия: 0.1. Дата: 15 октября 2026 года.

## 1. Цель

Общие инженерные правила находятся в [AGENTS.md](../AGENTS.md).

Цель прототипа — выделить самостоятельный сервис, который принимает уведомление, надёжно сохраняет его в собственной PostgreSQL и возвращает по идентификатору.

`created` означает «уведомление сохранено». Это не подтверждение отправки, доставки или прочтения.

Разработка следует порядку SDD: спецификация → сценарии приёмки → реализация → проверка. Доставка, авторизация и интеграция относятся к будущему развитию и не входят в критерии готовности прототипа.

## 2. Границы прототипа

Входит:

1. Самостоятельное Go-приложение в репозитории `sharetrip_notification`.
2. `POST /api/v1/notifications` — создание одной записи.
3. `GET /api/v1/notifications/{id}` — чтение одной записи.
4. Собственная БД PostgreSQL, одна таблица и начальная миграция Goose.
5. Валидация, единый формат ошибок, структурированные логи.
6. Makefile, локальная БД в Docker Compose, интеграционные тесты.

Не входит:

- Email, SMS, push, Telegram, шаблоны сообщений и любые адаптеры доставки.
- Статусы `sent`/`failed`, retry, очередь заданий и фоновые работники.
- Kafka/RabbitMQ, consumer событий, inbox/outbox этого сервиса.
- Вызовы notification из share-trip и изменение существующего outbox share-trip.
- Дедупликация POST, Idempotency-Key и гарантия exactly-once.
- Списки, фильтры, пагинация, изменение и удаление уведомлений.
- Пользовательский интерфейс, production-развёртывание и полный стек мониторинга.
- Keycloak и проверка прав получателя в этом локальном прототипе.

Решение по доступу: API предназначен для локальной демонстрации на loopback-интерфейсе. Любой локальный клиент может создать запись и прочитать её по ID. `recipient_id` — данные записи, а не доказательство личности вызывающего. Развёртывание за пределами локального окружения требует отдельного контракта аутентификации и авторизации.

## 3. Модель уведомления

| Поле | Тип API | Кто задаёт | Правило |
| --- | --- | --- | --- |
| `id` | Строка UUID | Сервис | Новый UUID v4 при каждом успешном создании |
| `recipient_id` | Строка | Клиент | Непустой идентификатор получателя; формат UUID не требуется |
| `type` | Строка | Клиент | Непустой тип уведомления, например `trip_published` |
| `status` | Строка | Сервис | Только `created` |
| `payload` | JSON-объект | Клиент или значение по умолчанию | Данные уведомления; при отсутствии `{}` |
| `created_at` | Строка времени | БД | Время создания, отдаётся в UTC, RFC 3339 с допустимой дробной частью |

Идентификаторы `client-123` и `trip-456` допустимы как данные клиента. Идентификатор самого уведомления `id` имеет формат UUID.

Решения по данным:

- `recipient_id` и `type` сохраняются с учётом регистра и без автоматического обрезания. Пустые строки и строки только из пробельных символов отклоняются.
- Типы уведомлений не ограничены `trip_published`; сервис не интерпретирует бизнес-смысл `payload` и не требует поле `trip_id`.
- Получатель и поездка не проверяются через share-trip или Keycloak. Межсервисных внешних ключей нет.
- Уведомление неизменно после создания в рамках доступного API.
- JSON сохраняется семантически: порядок ключей, пробелы и исходная запись чисел не гарантируются JSONB. Числа не должны терять точность из-за промежуточного преобразования в float64; значения за пределами возможностей JSONB отклоняются как некорректный запрос.

## 4. REST-контракт

Базовый локальный адрес по умолчанию: `http://127.0.0.1:8081`. Маршруты доступны без префиксов `/api` и `/v1`.

Все ответы используют оболочку share-trip: `data` и `errors`. При успехе `data` содержит объект уведомления, `errors` — пустой массив строк `[]`. При ошибке `data` равно `null`, а `errors` содержит сообщения об ошибках. Оба поля присутствуют всегда. Ответы с JSON используют `Content-Type: application/json`.

### 4.1. Создание

**POST /api/v1/notifications**, `Content-Type: application/json` (допустим параметр `charset`).

Пример запроса:

```json
{
  "recipient_id": "client-123",
  "type": "trip_published",
  "payload": {"trip_id": "trip-456"}
}
```

Успех: **201 Created**, заголовок `Location: /api/v1/notifications/{id}` и сохранённый объект:

```json
{
  "data": {
    "id": "e7e8bcc8-97c4-4abf-9d71-c7c5a19841d6",
    "recipient_id": "client-123",
    "type": "trip_published",
    "status": "created",
    "payload": {"trip_id": "trip-456"},
    "created_at": "2026-10-15T09:00:00Z"
  },
  "errors": []
}
```

Время и ID в примере иллюстративны. Ответ формируется из сохранённых значений, включая время БД, и отправляется только после успешного commit.

Правила валидации — решения прототипа:

- Тело обязательно и должно содержать ровно один JSON-объект.
- `recipient_id` и `type` обязательны, не могут быть null, другого типа, пустыми или состоять только из пробелов.
- `payload` можно опустить; тогда сохраняется `{}`. Явный null, массив, строка, число или boolean вместо объекта запрещены. Внутри объекта допустимы вложенные JSON-значения, включая null и массивы.
- Неизвестные поля верхнего уровня запрещены, в том числе `id`, `status`, `created_at`. Поля внутри payload произвольны.
- Максимальный размер всего тела — 64 KiB (65 536 байт). Дополнительные произвольные ограничения длины отдельных строк не вводятся.
- Отсутствующий или отличный от application/json Content-Type отклоняется.

| Код | Условие |
| --- | --- |
| 201 | Запись создана и транзакция зафиксирована |
| 400 | Ошибка JSON, полей или недопустимое для JSONB значение |
| 413 | Тело больше 64 KiB |
| 415 | Неподдерживаемый Content-Type |
| 500 | Неожиданная ошибка сервиса или БД |

Два одинаковых POST создают две записи с разными ID. При потере ответа после commit клиент не может определить исход запроса по этому API. Автоматический повтор может создать дубль; дедупликация остаётся отдельной будущей задачей.

### 4.2. Получение

**GET /api/v1/notifications/{id}** возвращает **200 OK** и ту же оболочку, что POST: объект уведомления в `data` и пустой массив `errors`.

Пример ответа для уведомления из примера POST:

```json
{
  "data": {
    "id": "e7e8bcc8-97c4-4abf-9d71-c7c5a19841d6",
    "recipient_id": "client-123",
    "type": "trip_published",
    "status": "created",
    "payload": {"trip_id": "trip-456"},
    "created_at": "2026-10-15T09:00:00Z"
  },
  "errors": []
}
```

| Код | Условие |
| --- | --- |
| 200 | Запись найдена |
| 400 | ID не соответствует канонической UUID-записи `8-4-4-4-12` |
| 404 | Синтаксически корректный UUID отсутствует в БД |
| 500 | Неожиданная ошибка сервиса или БД |

UUID в пути допускает верхний и нижний регистр hexadecimal-символов; в ответе приводится к нижнему. Нулевой UUID синтаксически допустим и при отсутствии записи даёт 404. GET не создаёт и не меняет данные.

### 4.3. Формат ошибок

Ошибки используют ту же оболочку, что и share-trip:

```json
{
  "data": null,
  "errors": ["recipient_id must be a non-empty string"]
}
```

`errors` — непустой массив строк при ошибке. Отдельные поля `error`, `code` и `message` не вводятся. Клиент определяет категорию ошибки по HTTP-статусу; текст сообщения служит для диагностики и не является машинным кодом.

Для 500 массив errors содержит только `internal server error`, без SQL, DSN, стека и внутренних ошибок. Ошибки разбора и middleware используют ту же структуру. При нескольких ошибках валидации достаточно сообщить одну; порядок не является контрактом.

Неизвестный маршрут возвращает 404, неподдерживаемый метод известного маршрута — 405 с заголовком Allow. HTTP-статусы сохраняются согласно таблицам выше; формат оболочки не меняет их семантику.

## 5. Хранение и миграции

Сервис владеет отдельной БД `sharetrip_notification`. Таблица `notifications` имеет следующую схему:

| Столбец | Тип PostgreSQL | Ограничения / значение по умолчанию |
| --- | --- | --- |
| id | UUID | PRIMARY KEY; генерируется приложением |
| recipient_id | TEXT | NOT NULL |
| type | TEXT | NOT NULL |
| status | TEXT | NOT NULL; приложение записывает created |
| payload | JSONB | NOT NULL DEFAULT '{}'::jsonb |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT now() |

Уточнение прототипа: добавить CHECK для непустых и не состоящих только из пробелов recipient_id/type, `status = 'created'` и объектного типа payload. Пробельными считаются символы Unicode White_Space, как в Go strings.TrimSpace: U+0009–U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000–U+200A, U+2028, U+2029, U+202F, U+205F, U+3000. SQL CHECK перечисляет этот набор явно и не зависит от локали БД. U+200B (zero-width space) не входит в набор. API использует strings.TrimSpace только для проверки пустоты, сохраняя исходные значения. Отдельная доменная валидация не вводится. Статус остаётся TEXT, PostgreSQL ENUM не требуется.

Достаточно индекса первичного ключа. Индексы по recipient_id/type и GIN по payload не нужны без соответствующих запросов. Нет history, outbox, delivery_attempts, updated_at и межсервисных FK.

Одна начальная миграция `<timestamp>_create_notifications.sql`: Up создаёт таблицу и ограничения; Down удаляет таблицу. Down разрушает данные и проверяется только на одноразовой БД. Миграции применяются отдельно от старта приложения через Goose. Применённые миграции не переписываются.

## 6. Архитектура и транзакции

Стек по AGENTS.md: Go 1.26, Fiber v2, pgx v5/pgxpool, PostgreSQL 16, Goose v3, UUID, slog, testing/testify и Testcontainers. Конкретные версии зависимостей фиксируются при реализации; полный стек share-trip автоматически не переносится.

| Компонент | Ответственность |
| --- | --- |
| cmd/notification | Конфигурация, ручная сборка зависимостей, запуск и остановка |
| internal/api | Маршруты, DTO, JSON и HTTP-ошибки |
| internal/service | CreateNotification/GetNotification, граница транзакции |
| internal/domain | В первой версии не требуется; появится только для самостоятельных бизнес-правил |
| internal/repository | SQL, пул, INSERT RETURNING и чтение по ID |
| internal/repository/entity | Представление строки notifications |
| internal/config, internal/app | Проверка окружения, настройка логгера |
| internal/api_test | Проверки HTTP-контракта и реальной БД |

Сохраняется слоистая модель AGENTS.md: API проверяет входной контракт, сервис назначает серверные поля и управляет транзакцией, репозиторий выполняет SQL. Отдельный доменный валидатор не нужен. Репозиторий получает context и транзакцию и не выполняет commit. Не нужны универсальный repository, брокер, scheduler или DI-контейнер.

Создание:

1. API разбирает и проверяет форму и поля запроса.
2. Сервис организует транзакцию, создаёт UUID и назначает created.
3. Репозиторий вставляет одну запись и возвращает фактические значения, включая created_at БД.
4. Сервис фиксирует транзакцию; только затем API возвращает 201.
5. При ошибке до commit выполняется rollback. Ошибка commit возвращается как 500; успешная запись при неопределённом результате commit не исключается.

Чтение выполняется в короткой транзакции через тот же подход к репозиториям, без блокировки FOR UPDATE. `pgx.ErrNoRows` переводится в предметную ошибку отсутствия. Ошибки оборачиваются с сохранением причины; контекст запроса проходит во все операции. Таймаут обращения к БД ограничивается контекстом запроса, по умолчанию 2 секунды. Таймаут БД в текущем контракте даёт 500, а не ложный 404.

## 7. Локальный запуск и эксплуатационный минимум

Приложение запускается на хосте, PostgreSQL — в Docker Compose с отдельным volume, healthcheck и именем проекта `sharetrip-notification`. Порт БД на хосте по умолчанию 6544, внутренний — 5432. Приложение и БД должны запускаться независимо от инфраструктуры share-trip.

| Параметр | Назначение |
| --- | --- |
| HTTP_HOST / HTTP_PORT | По умолчанию 127.0.0.1 / 8081 |
| DB_HOST / DB_PORT / DB_NAME | По умолчанию localhost / 6544 / sharetrip_notification |
| DB_USER / DB_PASSWORD | Обязательные параметры доступа |
| DB_SSLMODE | Для локального окружения disable |
| POSTGRES_USER / POSTGRES_PASSWORD / POSTGRES_DB / POSTGRES_PORT | Согласованные настройки Compose |
| GOOSE_DRIVER / GOOSE_DBSTRING | postgres и DSN той же локальной БД |

Секреты хранятся в локальном .env, исключённом из Git. `.env.example` описывает параметры без настоящих секретов. Значения по умолчанию применяются только к отсутствующим переменным; явно пустые или пробельные HTTP_HOST, DB_HOST, DB_NAME, DB_USER и DB_PASSWORD отклоняются. Пароль сохраняется без обрезания. HTTP_PORT и DB_PORT принимают целые значения от 1 до 65535. DB_SSLMODE допускает disable, allow, prefer, require, verify-ca и verify-full; остальные значения отклоняются. Ошибки называют параметр, но не выводят его значение или DSN. Ошибка обязательной конфигурации или недоступность БД при старте завершает процесс с ненулевым кодом. БД должна быть мигрирована до запуска приложения.

Обязательные цели будущего Makefile: help, deps, tidy, fmt, lint, test, build, run, up, down, migrate-create, migrate-status, migrate-up, migrate-down. Инструменты устанавливаются в .tools с фиксированными версиями; бинарный файл — bin/notification с учётом Windows .exe. Обычный down сохраняет volume. Dockerfile приложения и Compose для наблюдаемости не требуются на этом этапе.

Логи — JSON в stdout: операция, результат, длительность, request ID и при наличии notification ID. Request ID генерируется сервисом для каждого запроса и возвращается как X-Request-Id. Полный payload и секреты не логируются. Не требуется файловый LOG_FILE, Loki, Prometheus или OTel: они могут быть добавлены позже без изменения бизнес-контракта.

Завершение процесса по сигналу прекращает приём новых запросов, даёт текущим запросам до 5 секунд и закрывает пул. Фоновых работников нет. Отдельные технические HTTP-маршруты не являются частью минимального контракта.

## 8. Связь с share-trip

В share-trip публикация поездки сохраняет `trip_published` в outbox; текущий payload содержит только `trip_id`. Отправщик пока отсутствует. Это результат анализа кода share-trip, а не реализованная интеграция notification.

Для будущего преобразования события в запрос уведомления ещё предстоит определить recipient_id, правила выбора получателей и ключ дедупликации. Текущего payload для этого недостаточно. Прототип не читает таблицы share-trip и не добавляет получателей автоматически.

Контракт проверяется HTTP-запросами POST и GET; сохранение и транзакции дополнительно проверяются прямыми запросами к тестовой БД. Недоступность share-trip или Keycloak не влияет на создание и чтение локального уведомления.

## 9. Сценарии приёмки

Для будущих интеграционных тестов требуется настоящий PostgreSQL 16 в Testcontainers и миграции сервиса. Сейчас тесты конфигурации, схемы и helper Testcontainers удалены пользователем; автоматического покрытия в репозитории нет. Таблица ниже задаёт ожидаемое поведение, а не отчёт о выполненных тестах.

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| AC-01 | POST с корректными данными | 201, объект с UUID и created в data, errors = [], Location; в БД ровно одна соответствующая запись |
| AC-02 | GET созданного ID | 200; data совпадает с data из POST, включая created_at; errors = [] |
| AC-03 | POST без payload / с пустым объектом | 201; payload равен {} |
| AC-04 | Нет recipient_id/type, null, неверный тип, пустая или пробельная строка | 400; data = null, errors содержит сообщение; запись не появляется |
| AC-05 | Повреждённый JSON, пустое тело, массив или несколько JSON-значений | 400; запись не появляется |
| AC-06 | payload равен null, массиву или скаляру | 400; запись не появляется |
| AC-07 | Неизвестное поле верхнего уровня, в том числе status/id/created_at | 400; клиент не назначает серверные поля |
| AC-08 | Другой непустой type, строковый recipient_id, вложенный payload | 201; данные сохранены без обращения к другим сервисам |
| AC-09 | GET неизвестного UUID / невалидного UUID | 404 / 400; data = null, errors содержит сообщение |
| AC-10 | Два одинаковых POST, в том числе параллельных | Два ответа 201, разные ID, две записи |
| AC-11 | Перезапуск приложения при сохранённой БД | GET ранее созданной записи возвращает 200 |
| AC-12 | Ошибка БД при POST или GET | 500 с безопасным сообщением; внутренние детали только в логах |
| AC-13 | Принудительная ошибка до commit после INSERT | Rollback, запись отсутствует; helper не возвращает успех |
| AC-14 | Превышение 64 KiB / неподдерживаемый Content-Type | 413 / 415, единый формат ошибки |
| AC-15 | Неизвестный маршрут / неподдерживаемый метод | 404 / 405; data = null, errors содержит сообщение |
| AC-16 | Чистая БД, цикл Up → Down → Up | Схема создаётся повторно; ограничения отвергают недопустимые данные |
| AC-17 | Точные числовые значения и вложенные данные в payload | GET сохраняет семантику JSON без потери точности числа |
| AC-18 | Запуск без обязательной конфигурации или без БД | Ненулевой код завершения и понятная диагностическая запись |

Интеграционные тесты изолируют данные уникальными ID и не очищают общие таблицы параллельно. Тесты не требуют запущенных share-trip, Keycloak и каналов доставки. Отдельно проверяются ограничения БД, обработка ошибок транзакции и очистка ресурсов.
