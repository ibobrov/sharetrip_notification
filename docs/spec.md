# Спецификация начального прототипа sharetrip_notification

Статус: контракт 09.5 и жизненный цикл задачи 10 приняты; задача 11 готова к приёмке. Версия: 0.4. Дата: 17 октября 2026 года.

## 1. Цель

Общие инженерные правила находятся в [AGENTS.md](../AGENTS.md).

Цель прототипа — выделить самостоятельный сервис, который принимает уведомление, надёжно сохраняет его в собственной PostgreSQL и возвращает по идентификатору.

`created` означает «уведомление сохранено». Это не подтверждение отправки, доставки или прочтения.

Разработка следует порядку SDD: спецификация → сценарии приёмки → реализация → проверка. Доставка, авторизация и интеграция относятся к будущему развитию и не входят в критерии готовности прототипа.

## 2. Границы прототипа

Входит:

1. Самостоятельное Go-приложение в репозитории `sharetrip_notification`.
2. `POST /api/v1/notifications` — создание одной записи.
3. `GET /api/v1/notifications/{id}` — чтение одной записи.
4. Собственная БД PostgreSQL, одна таблица и начальная миграция Goose.
5. Валидация DTO через govalidator и структурированные логи.
6. Makefile, локальная БД в Docker Compose, интеграционные тесты.

Не входит:

- Email, SMS, push, Telegram, шаблоны сообщений и любые адаптеры доставки.
- Статусы `sent`/`failed`, retry, очередь заданий и фоновые работники.
- Kafka/RabbitMQ, consumer событий, inbox/outbox этого сервиса.
- Вызовы notification из share-trip и изменение существующего outbox share-trip.
- Дедупликация POST, Idempotency-Key и гарантия exactly-once.
- Списки, фильтры, пагинация, изменение и удаление уведомлений.
- Пользовательский интерфейс, production-развёртывание и полный стек мониторинга.
- Keycloak и проверка прав получателя в этом локальном прототипе.

Решение по доступу: API предназначен для локальной демонстрации на loopback-интерфейсе. Любой локальный клиент может создать запись и прочитать её по ID. `recipient_id` — данные записи, а не доказательство личности вызывающего. Развёртывание за пределами локального окружения требует отдельного контракта аутентификации и авторизации.

## 3. Модель уведомления

| Поле | Тип API | Кто задаёт | Правило |
| --- | --- | --- | --- |
| `id` | Строка UUID | Сервис | Новый UUID v4 при каждом успешном создании |
| `recipient_id` | Строка | Клиент | Обязательный идентификатор получателя; формат UUID не требуется |
| `type` | Строка | Клиент | Обязательный тип уведомления, например `trip_published` |
| `status` | Строка | Сервис | Только `created` |
| `payload` | JSON | Клиент или значение по умолчанию | Данные уведомления; при отсутствии `{}` |
| `created_at` | Строка времени | БД | Время создания, отдаётся в UTC, RFC 3339 с допустимой дробной частью |

Идентификаторы `client-123` и `trip-456` допустимы как данные клиента. Идентификатор самого уведомления `id` имеет формат UUID.

Решения по данным:

- `recipient_id` и `type` проверяются govalidator с правилом `required`, сохраняются без автоматического обрезания и дополнительных ручных проверок.
- Типы уведомлений не ограничены `trip_published`; сервис не интерпретирует бизнес-смысл `payload` и не требует поле `trip_id`.
- Получатель и поездка не проверяются через share-trip или Keycloak. Межсервисных внешних ключей нет.
- Уведомление неизменно после создания в рамках доступного API.
- Payload передаётся в PostgreSQL JSONB без отдельного API-валидатора его структуры.

## 4. REST-контракт

Базовый локальный адрес по умолчанию: `http://127.0.0.1:8081`. Маршруты первой версии используют префикс `/api/v1`. Успешный ответ содержит объект уведомления напрямую, без оболочки `{data, errors}`.

### 4.1. Создание

**POST /api/v1/notifications** принимает JSON-тело. Отдельной проверки Content-Type и размера тела в API нет.

Пример запроса:

```json
{
  "recipient_id": "client-123",
  "type": "trip_published",
  "payload": {"trip_id": "trip-456"}
}
```

Успех: **201 Created** и сохранённый объект:

```json
{
  "id": "e7e8bcc8-97c4-4abf-9d71-c7c5a19841d6",
  "recipient_id": "client-123",
  "type": "trip_published",
  "status": "created",
  "payload": {"trip_id": "trip-456"},
  "created_at": "2026-10-15T09:00:00Z"
}
```

Время и ID в примере иллюстративны. Ответ формируется из сохранённых значений, включая время БД, и отправляется только после успешного commit.

Fiber разбирает тело в DTO. `recipient_id` и `type` проверяются govalidator с правилом `required`. При отсутствии payload API передаёт `{}`. Дополнительных ручных проверок полей, неизвестных ключей и структуры payload нет.

| Код | Условие |
| --- | --- |
| 201 | Запись создана и транзакция зафиксирована |
| 400 | Некорректное тело или ошибка govalidator |
| 500 | Неожиданная ошибка сервиса или БД |

### 4.2. Получение

**GET /api/v1/notifications/{id}** возвращает **200 OK** и объект уведомления напрямую.

Пример ответа для уведомления из примера POST:

```json
{
  "id": "e7e8bcc8-97c4-4abf-9d71-c7c5a19841d6",
  "recipient_id": "client-123",
  "type": "trip_published",
  "status": "created",
  "payload": {"trip_id": "trip-456"},
  "created_at": "2026-10-15T09:00:00Z"
}
```

| Код | Условие |
| --- | --- |
| 200 | Запись найдена |
| 400 | `id` не прошёл UUID-валидацию govalidator |
| 404 | Корректный UUID отсутствует в БД |
| 500 | Неожиданная ошибка сервиса или БД |

GET не создаёт и не меняет данные.

### 4.3. Формат ошибок

Отдельный JSON-формат ошибок не задан. Fiber возвращает текст ошибки и соответствующий статус. Внутренние причины ошибок сервиса и БД клиенту не выдаются.

## 5. Хранение и миграции

Сервис владеет отдельной БД `sharetrip_notification`. Таблица `notifications` имеет следующую схему:

| Столбец | Тип PostgreSQL | Ограничения / значение по умолчанию |
| --- | --- | --- |
| id | UUID | PRIMARY KEY; генерируется приложением |
| recipient_id | TEXT | NOT NULL |
| type | TEXT | NOT NULL |
| status | TEXT | NOT NULL; приложение записывает created |
| payload | JSONB | NOT NULL DEFAULT '{}'::jsonb |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT now() |

В первой версии CHECK для `recipient_id`, `type`, `status` и формы `payload` не добавляются. API использует только правила DTO govalidator, PostgreSQL независимо проверяет корректность значения JSONB и базовые ограничения столбцов. Отдельная доменная валидация не вводится. Статус остаётся TEXT, PostgreSQL ENUM не требуется.

Достаточно индекса первичного ключа. Индексы по recipient_id/type и GIN по payload не нужны без соответствующих запросов. Нет history, outbox, delivery_attempts, updated_at и межсервисных FK.

Одна начальная миграция `<timestamp>_create_notifications.sql`: Up создаёт таблицу и ограничения; Down удаляет таблицу. Down разрушает данные и проверяется только на одноразовой БД. Миграции применяются отдельно от старта приложения через Goose. Применённые миграции не переписываются.

## 6. Архитектура и транзакции

Стек по AGENTS.md: Go 1.26, Fiber v2, govalidator v12, pgx v5/pgxpool, PostgreSQL 16, Goose CLI v3, godotenv, UUID, slog и testing. Testcontainers подключается только для задач с интеграционной проверкой PostgreSQL.

| Компонент | Ответственность |
| --- | --- |
| cmd/notification | Конфигурация, ручная сборка зависимостей, запуск и остановка |
| internal/api | Маршруты, DTO, JSON, HTTP-ошибки, request ID и лог запроса |
| internal/service | CreateNotification/GetNotification, граница транзакции |
| internal/domain | В первой версии не требуется; появится только для самостоятельных бизнес-правил |
| internal/repository | SQL, пул, INSERT RETURNING и чтение по ID |
| internal/repository/entity | Представление строки notifications |
| internal/config, internal/app | Проверка окружения, JSON-логгер и жизненный цикл Fiber |

Сохраняется слоистая модель AGENTS.md: API проверяет входной контракт, сервис назначает серверные поля и управляет транзакцией, репозиторий выполняет SQL. Отдельный доменный валидатор не нужен. Репозиторий получает context и транзакцию и не выполняет commit. Не нужны универсальный repository, брокер, scheduler или DI-контейнер.

Создание:

1. API разбирает запрос средствами Fiber и проверяет DTO через govalidator.
2. Сервис организует транзакцию, создаёт UUID и назначает created.
3. Репозиторий вставляет одну запись и возвращает фактические значения, включая created_at БД.
4. Сервис фиксирует транзакцию; только затем API возвращает 201.
5. При ошибке до commit выполняется rollback. Ошибка commit возвращается как 500; успешная запись при неопределённом результате commit не исключается.

Чтение выполняется в короткой транзакции через тот же подход к репозиториям, без блокировки FOR UPDATE. `pgx.ErrNoRows` переводится в предметную ошибку отсутствия. Контекст запроса проходит во все операции.

## 7. Локальный запуск и эксплуатационный минимум

Приложение запускается на хосте, PostgreSQL — в Docker Compose с отдельным volume, healthcheck и именем проекта `sharetrip-notification`. Порт БД на хосте по умолчанию 6544, внутренний — 5432. Приложение и БД должны запускаться независимо от инфраструктуры share-trip.

| Параметр | Назначение |
| --- | --- |
| HTTP_HOST / HTTP_PORT | По умолчанию 127.0.0.1 / 8081 |
| DB_HOST / DB_PORT / DB_NAME | По умолчанию localhost / 6544 / sharetrip_notification |
| DB_USER / DB_PASSWORD | Обязательные параметры доступа |
| DB_SSLMODE | Для локального окружения disable |
| POSTGRES_USER / POSTGRES_PASSWORD / POSTGRES_DB / POSTGRES_PORT | Согласованные настройки Compose |
| GOOSE_DRIVER / GOOSE_DBSTRING | postgres и DSN той же локальной БД |

Секреты хранятся в локальном .env, исключённом из Git. `.env.example` описывает параметры без настоящих секретов. Значения по умолчанию применяются только к отсутствующим переменным; явно пустые или пробельные HTTP_HOST, DB_HOST, DB_NAME, DB_USER и DB_PASSWORD отклоняются. Пароль сохраняется без обрезания. HTTP_PORT и DB_PORT принимают целые значения от 1 до 65535. DB_SSLMODE допускает disable, allow, prefer, require, verify-ca и verify-full; остальные значения отклоняются. Ошибки называют параметр, но не выводят его значение или DSN. Ошибка обязательной конфигурации или недоступность БД при старте завершает процесс с ненулевым кодом. БД должна быть мигрирована до запуска приложения.

Makefile содержит цели help, deps, tidy, fmt, lint, test, build, run, up, down, migrate-create, migrate-status, migrate-up и migrate-down. Инструменты устанавливаются в .tools с фиксированными версиями; бинарный файл — bin/notification с учётом Windows .exe. Обычный down сохраняет volume. Dockerfile приложения и Compose для наблюдаемости не требуются на этом этапе.

Логи — JSON в stdout: операция, результат, длительность, request ID и при наличии notification ID. Request ID генерируется сервисом для каждого запроса и возвращается как X-Request-Id. Полный payload и секреты не логируются. Не требуется файловый LOG_FILE, Loki, Prometheus или OTel: они могут быть добавлены позже без изменения бизнес-контракта.

Завершение процесса по сигналу прекращает приём новых запросов, даёт текущим запросам до 5 секунд и закрывает пул. Фоновых работников нет. Отдельные технические HTTP-маршруты не являются частью минимального контракта.

## 8. Связь с share-trip

В share-trip публикация поездки сохраняет `trip_published` в outbox; текущий payload содержит только `trip_id`. Отправщик пока отсутствует. Это результат анализа кода share-trip, а не реализованная интеграция notification.

Для будущего преобразования события в запрос уведомления ещё предстоит определить recipient_id, правила выбора получателей и ключ дедупликации. Текущего payload для этого недостаточно. Прототип не читает таблицы share-trip и не добавляет получателей автоматически.

Контракт проверяется HTTP-запросами POST и GET; сохранение и транзакции дополнительно проверяются прямыми запросами к тестовой БД. Недоступность share-trip или Keycloak не влияет на создание и чтение локального уведомления.

## 9. Сценарии приёмки

Интеграционный тест PostgreSQL задачи 09.5 и тесты жизненного цикла задачи 10 удалены после приёмки. Интеграционный тест задачи 11 проверяет POST, прямое чтение PostgreSQL и GET после пересоздания HTTP-приложения и пула соединений; он сохранён до приёмки задачи.

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| AC-01 | POST с корректными данными | 201, прямой объект с UUID и created; в БД есть соответствующая запись |
| AC-02 | GET созданного ID | 200; прямой объект совпадает с ответом POST |
| AC-03 | POST без payload / с пустым объектом | 201; payload равен {} |
| AC-04 | Нет обязательного recipient_id или type, либо повреждён JSON | 400 с ошибкой BodyParser или govalidator |
| AC-05 | GET с некорректным id | 400 с ошибкой валидации |
| AC-06 | GET с корректным отсутствующим UUID | 404 |
| AC-07 | Ошибка сервиса или БД при POST или GET | 500 без внутренних деталей |
| AC-08 | Перезапуск приложения при сохранённой БД | GET ранее созданной записи возвращает 200 |
| AC-09 | Принудительная ошибка до commit после INSERT | Rollback, запись отсутствует; helper не возвращает успех |
| AC-10 | Запуск без обязательной конфигурации или без БД | Ненулевой код завершения и понятная диагностическая запись |

Интеграционные тесты изолируют данные уникальными ID и не очищают общие таблицы параллельно. Тесты не требуют запущенных share-trip, Keycloak и каналов доставки. Отдельно проверяются ограничения БД, обработка ошибок транзакции и очистка ресурсов.

## 10. План реализации

1. Зафиксировать модуль, каркас каталогов, зависимости, конфигурацию, Makefile и локальный Compose.
2. Создать начальную миграцию notifications и тестовую инфраструктуру PostgreSQL.
3. Реализовать модель, инварианты, репозиторий и сервисные операции с транзакциями.
4. Реализовать HTTP-контракт, обработку ошибок, логи и завершение процесса.
5. Проверить сценарии AC-01–AC-10, выполнить форматирование, lint, сборку и тесты.
6. Описать в README настройку окружения, команды запуска и демонстрацию POST → GET → перезапуск → GET.

Прототип считается готовым, когда он запускается по README с нуля, выполняет два метода согласно спецификации, сохраняет данные между перезапусками, проходит критерии приёмки и не требует внешних сервисов доставки. Изменения контракта сначала вносятся в спецификацию, затем в реализацию и тесты.
