# 09.5. Упростить HTTP API по контракту учебного задания

Статус: к выполнению; реализацию начинать только после явного подтверждения пользователя.
Зависимости: 09.
Основание: разделы 6–8 документа «Зачем мы дробим процесс» и уточнение пользователя от 16 октября 2026 года.

## Причина

Постановка задачи 09 была расширена требованиями, которых нет в исходном учебном задании. Текущее решение содержит ручную валидацию, дополнительные HTTP-статусы, общую оболочку ответа, лимит тела, проверку Content-Type и другие несогласованные правила. Их нужно удалить, сохранив только минимальный контракт документа.

## Целевой контракт

- `POST /api/v1/notifications` принимает `recipient_id`, `type` и `payload` и возвращает сохранённое уведомление напрямую в JSON с HTTP 201.
- Для POST используются только указанные в документе ошибки: HTTP 400 для некорректного тела и HTTP 500 для внутренней ошибки.
- `GET /api/v1/notifications/{id}` возвращает уведомление напрямую в JSON с HTTP 200.
- Для GET используются HTTP 400 с ошибкой валидации для некорректного `id`, HTTP 404 для корректного `id`, по которому нет уведомления, и HTTP 500 для внутренней ошибки.
- Формат тела ошибки документом не задан. Не вводить собственную оболочку или дополнительные поля без отдельного явного согласования.
- Схема хранения остаётся минимальной: UUID primary key, `recipient_id`, `type`, `status`, JSONB `payload` с default `{}` и `created_at`.

## Объём рефакторинга

- Сохранить существующий префикс `/api/v1` и маршруты `/api/v1/notifications` и `/api/v1/notifications/{id}`.
- Убрать ручные функции проверки `recipient_id`, `type`, `payload`, неизвестных полей, единственного JSON-значения и канонической формы UUID.
- Разбирать запрос средствами Fiber и валидировать DTO через `github.com/asaskevich/govalidator/v12` по образцу share-trip.
- `govalidator` сейчас отсутствует в `go.mod` sharetrip_notification. При реализации задачи добавить версию `v12.0.0`, используемую в share-trip, и применять её для последующей API-валидации вместо новых ручных валидаторов.
- Ограничить validation tags только требованиями исходного документа. Не добавлять проверки формата, длины, регистра, пробельных строк, неизвестных полей или структуры вложенного payload без явного согласования.
- Убрать проверку `Content-Type: application/json`, включая разбор charset.
- Убрать лимит тела 65 536 байт и специальный ответ HTTP 413.
- Убрать HTTP 415, специальную обработку 405 с `Allow`, собственный 404 для неизвестного маршрута и остальные статусы, отсутствующие в документе.
- Убрать оболочку `{data, errors}` и возвращать объект уведомления напрямую, как в примерах документа.
- Убрать заголовок `Location`, двухсекундный timeout обработчика и классификацию ошибок JSONB в 400: этих требований в документе нет.
- Не добавлять новые middleware, форматы ошибок, ограничения или сценарии совместимости в рамках рефакторинга.
- Обновить `docs/spec.md`, `AGENTS.md`, README и следующие задачи так, чтобы они описывали только целевой минимальный контракт.

## Подтверждённые уточнения пользователя

- Префикс `/api/v1` удалять не нужно.
- Некорректный `id` возвращает HTTP 400 и ошибку валидации.
- Корректный `id`, для которого нет данных, возвращает HTTP 404.

## Проверки при реализации

- [ ] Проверить успешный POST `/api/v1/notifications`: HTTP 201, прямой JSON-объект и строка в PostgreSQL.
- [ ] Проверить некорректное тело и ошибки `govalidator`: HTTP 400 без дополнительного придуманного контракта.
- [ ] Проверить внутреннюю ошибку POST: HTTP 500.
- [ ] Проверить успешный GET `/api/v1/notifications/{id}`: HTTP 200 и прямой JSON-объект.
- [ ] Проверить некорректный `id`: HTTP 400 с ошибкой валидации; корректный отсутствующий `id`: HTTP 404; внутреннюю ошибку GET: HTTP 500.
- [ ] Проверить отсутствие ручных валидаторов, лимита 65 536 байт, проверки Content-Type, `Location` и оболочки `{data, errors}`.
- [ ] Проверить `go mod tidy`, форматирование, lint, сборку и подходящие тесты.

## Критерий готовности

HTTP API соответствует только разделам 6–8 исходного документа и явно согласованным уточнениям пользователя. Любое новое поведение сначала отдельно согласуется, затем добавляется в постановку и код.
