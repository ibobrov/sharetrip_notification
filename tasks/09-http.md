# 09. Реализовать POST и GET уведомлений

Статус: к выполнению.
Зависимости: 01, 08.
Основание: [план первой версии](README.md), [спецификация](../docs/spec.md), [правила разработки](../AGENTS.md).

## Цель

Связать HTTP-контракт с сервисными операциями и единым форматом ответов.

## Объём работ

- Добавить POST /notifications без префикса /api; тело — один JSON-объект.
- Проверять Content-Type application/json с допустимым charset, размер до 65 536 байт, обязательные и неизвестные поля верхнего уровня.
- Отсутствующий payload отличать от явного null. Запретить клиентские id/status/created_at.
- Вернуть 201 с полным объектом в data (id, recipient_id, type, status, payload, created_at), errors=[] и Location: /notifications/{id}. Ошибки: data=null, errors — непустой массив строк.
- Обработать 400/413/415/500, неизвестный маршрут 404 и неподдерживаемый метод 405 с Allow; использовать одну оболочку также для ошибок middleware.
- Не раскрывать SQL/DSN/внутренние ошибки; для 500 отдавать internal server error. Передавать контекст с таймаутом 2 секунды.

- Добавить GET /notifications/{id}: 200 с тем же объектом, 400 для некорректного UUID, 404 для отсутствующей записи и 500 для сбоя БД. Соблюдать правила UUID из спецификации.

## Проверки

- [ ] HTTP + PostgreSQL: успешный POST и проверка записи по возвращённому data.id.
- [ ] Табличные тесты всех невалидных полей, повреждённого JSON, нескольких значений и неизвестных полей; записей не появляется.
- [ ] Проверить тело на границе лимита и выше, Content-Type, 404/405 и оболочку всех ошибок.
- [ ] Проверить сбой БД: 500 без внутренних деталей; проверить параллельные одинаковые POST.

- [ ] Проверить POST → GET: совпадают все поля, включая created_at и вложенный payload, errors=[].
- [ ] Проверить GET: неизвестный UUID, неверный формат, регистр UUID, нулевой UUID, ошибка БД; чтение не меняет запись.

## Критерий готовности

Контракт полностью соблюдён; HTTP-слой не содержит SQL и не управляет транзакциями.
