# 09. Реализовать POST и GET уведомлений

Статус: постановка отозвана; расширенная реализация заменена задачей 09.5, прежний тест удалён.
Зависимости: 01, 08.
Основание: [план первой версии](README.md), [спецификация](../docs/spec.md), [правила разработки](../AGENTS.md).

## Цель

Связать HTTP-контракт с сервисными операциями и единым форматом ответов.

## Объём работ

- Создать группу маршрутов `/api/v1/notifications` по аналогии с группировкой маршрутов в trip service. Добавить `POST /api/v1/notifications`; тело — один JSON-объект.
- Проверять Content-Type application/json с допустимым charset, размер до 65 536 байт, обязательные и неизвестные поля верхнего уровня.
- Проверять `recipient_id` и `type`: обязательные строки, не пустые и не состоящие только из пробельных символов; исходные значения и регистр не менять.
- Проверять `payload` в API: отсутствие заменять на `{}`; явный `null`, массив, строку, число и boolean отклонять; вложенные значения внутри объекта разрешать. JSON передавать дальше без преобразования чисел через `float64`.
- Отсутствующий payload отличать от явного null. Запретить клиентские id/status/created_at.
- Не создавать отдельный доменный валидатор или доменные ошибки валидации. Ограничения хранения JSONB проверяет PostgreSQL; API безопасно преобразует соответствующую ошибку сохранения в 400.
- Вернуть 201 с полным объектом в data (id, recipient_id, type, status, payload, created_at), errors=[] и `Location: /api/v1/notifications/{id}`. Ошибки: data=null, errors — непустой массив строк.
- Обработать 400/413/415/500, неизвестный маршрут 404 и неподдерживаемый метод 405 с Allow; использовать одну оболочку также для ошибок middleware.
- Не раскрывать SQL/DSN/внутренние ошибки; для 500 отдавать internal server error. Передавать контекст с таймаутом 2 секунды.

- Добавить `GET /api/v1/notifications/{id}`: 200 с тем же объектом, 400 для некорректного UUID, 404 для отсутствующей записи и 500 для сбоя БД. Соблюдать правила UUID из спецификации.

## Проверки

- [x] HTTP + PostgreSQL: успешный POST и проверка записи по возвращённому data.id.
- [x] Табличные тесты всех невалидных полей, повреждённого JSON, нескольких значений и неизвестных полей; записей не появляется.
- [x] Проверить тело на границе лимита и выше, Content-Type, 404/405 и оболочку всех ошибок.
- [x] Проверить сбой БД: 500 без внутренних деталей; проверить параллельные одинаковые POST.

- [x] Проверить POST → GET: совпадают все поля, включая created_at и вложенный payload, errors=[].
- [x] Проверить GET: неизвестный UUID, неверный формат, регистр UUID, нулевой UUID, ошибка БД; чтение не меняет запись.

## Критерий готовности

Контракт полностью соблюдён; HTTP-слой не содержит SQL и не управляет транзакциями.

Добавлены `internal/api/router.go` и `notification.go`. Fiber-маршруты `POST /api/v1/notifications` и `GET /api/v1/notifications/{id}` используют сервисный интерфейс, не содержат SQL и не управляют транзакциями. API проверяет Content-Type, лимит 65 536 байт, единственный JSON-объект, известные поля, строки `recipient_id`/`type`, объектный `payload` и канонический UUID.
