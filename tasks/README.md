# План первой версии сервиса уведомлений

Статус: задачи 01–04 выполнены; задачи 05–11 запланированы. Созданы каркас, пакет конфигурации с тестами, Makefile и локальная PostgreSQL в Compose. HTTP, схема и подключение приложения к БД ещё не реализованы. Дата: 16 октября 2026 года.

Целевой сценарий: POST /notifications → валидация → сохранение в PostgreSQL → HTTP 201 → GET /notifications/{id} → HTTP 200. Оба ответа содержат полный объект уведомления в data (id, recipient_id, type, status, payload, created_at), errors=[].

[Спецификация](../docs/spec.md) определяет создание и получение уведомления в первой версии. Идентификатор в API и БД называется id. Доставка, брокер, outbox, Keycloak и дедупликация в этот этап не входят.

## Общие правила проверки

- Unit-тесты проверяют правила и конфигурацию; SQL и транзакции — настоящий PostgreSQL 16 в Testcontainers с теми же миграциями.
- HTTP-тесты проверяют и ответ, и фактическое состояние БД. Отдельно проверяется сценарий POST → GET и ошибки чтения.
- Изолировать данные тестов; не очищать общие таблицы одновременно с параллельными сценариями.
- Изменяющие окружение тесты выполнять последовательно. Down миграции проверять только на одноразовой БД.
- Финальная проверка: make fmt, make lint, make build, make test и сценарий запуска по README.

## Локальный запуск после реализации

1. Установить Go, Make, запустить Docker; создать .env по .env.example.
2. Согласовать DB_*, POSTGRES_* и Goose: БД sharetrip_notification на localhost:6544; приложение на 127.0.0.1:8081.
3. Выполнить make deps, make up, make migrate-status, make migrate-up.
4. Выполнить make lint, make build, make test, затем make run.
5. Отправить POST, выполнить GET по data.id, сравнить объекты и проверить строку в PostgreSQL.
6. Перезапустить приложение, повторить GET и проверить сохранность данных.
7. Остановить приложение и выполнить make down без удаления volume.
