# Правила разработки sharetrip_notification

Контекст репозитория на 15 октября 2026 года: подготовлены спецификация и постановки задач. Go-код, go.mod, миграции, Makefile и Compose ещё не созданы. Стек, структура и команды ниже описывают целевую реализацию; не представляй их как уже существующие.

## 1. Источники требований и объём первой версии

- [docs/spec.md](docs/spec.md) — спецификация поведения и хранения.
- [tasks/README.md](tasks/README.md) — согласованный план первой версии и зависимости задач.
- [tasks/01-contract.md](tasks/01-contract.md) — синхронизация спецификации с текущим объёмом.
- Остальные постановки в tasks содержат объём работ, проверки и критерии готовности отдельных задач.

Первая версия включает POST /notifications и GET /notifications/{id}. Оба метода возвращают полный объект уведомления в data: id, recipient_id, type, status, payload, created_at; errors=[]. Контракт определяется docs/spec.md.

Первая версия принимает запрос создания, валидирует его, сохраняет уведомление в собственной PostgreSQL и предоставляет получение по id. Статус created означает сохранение, а не доставку.

Внешние каналы доставки, брокер, фоновые работники, outbox/inbox, retry, дедупликация и Keycloak не входят в первую версию. Для проверок сохранения используй прямое чтение тестовой БД. Сервис не должен зависеть от запуска других прикладных сервисов.

## 2. Целевой стек

| Область | Решение |
| --- | --- |
| Язык | Go 1.26, Go Modules |
| HTTP | Fiber v2, стандартный encoding/json для работы с JSON |
| Хранение | PostgreSQL 16, pgx v5/pgxpool, явный SQL без ORM |
| Миграции | Goose v3, SQL с Up/Down |
| Идентификаторы | UUID v4, github.com/google/uuid |
| Конфигурация | Переменные окружения, локальный .env |
| Логи | log/slog, JSON в stdout |
| Тесты | testing, testify, Testcontainers с PostgreSQL |
| Инструменты | Make, golangci-lint v2, Docker Compose v2 |

Точные версии фиксируй при создании go.mod и Makefile. Добавляй библиотеки только для конкретной потребности. Не переноси зависимости другого сервиса целиком. Prometheus, OTel, Loki, Grafana и файловый LOG_FILE для первой версии не требуются.

## 3. Архитектура

Поток операции: HTTP → api → service → domain/repository → PostgreSQL. Применяй слоистую архитектуру с ручной сборкой зависимостей. Она допускает передачу pgx.Tx и конкретные репозитории; независимость домена от инфраструктуры не является отдельной целью.

Планируемая структура:

```text
cmd/notification/main.go       # конфигурация, сборка зависимостей, запуск
internal/api/                  # маршруты, HTTP DTO, ответы и ошибки
internal/service/              # прикладная операция и транзакционный helper
internal/domain/               # инварианты уведомления, предметные ошибки
internal/repository/           # пул и SQL
internal/repository/entity/    # представление строки notifications
internal/config/               # чтение и проверка окружения
internal/app/                  # логгер и инфраструктурная сборка
internal/api_test/             # интеграционные HTTP/БД-тесты
migrations/                    # миграции Goose
deploy/docker-compose.yml      # локальная PostgreSQL
docs/spec.md                   # контракт сервиса
tasks/                         # постановки и порядок выполнения
```

- main собирает зависимости через конструкторы и управляет жизненным циклом; бизнес-правила находятся вне точки входа.
- api разбирает JSON, проверяет транспортные ограничения, преобразует DTO и вызывает service. SQL и транзакции в обработчике запрещены.
- service координирует создание и получение и владеет границей транзакции.
- domain проверяет поля уведомления и инвариант статуса created.
- repository выполняет параметризованный SQL, принимает контекст и транзакцию, не выбирает HTTP-статусы и не делает commit.
- Разделяй HTTP DTO и структуры хранения. Идентификатор называется id и в БД, и в HTTP-ответе.
- Создавай файлы по необходимости, без фиктивных реализаций для заполнения каталогов. Не вводи универсальный repository или DI-фреймворк.

## 4. Контракт первой версии

POST /notifications принимает recipient_id, type и необязательный payload.

- recipient_id/type — обязательные непустые строки, не состоящие только из пробельных символов. Сохраняй регистр и исходное значение. recipient_id не обязан быть UUID.
- type — произвольная непустая строка. Сервис не интерпретирует trip_published как особый сценарий и не проверяет существование получателя или поездки.
- Отсутствующий payload превращается в {}. Явный null, массив и скаляры запрещены; вложенные JSON-значения внутри объекта допустимы.
- Тело содержит ровно один JSON-объект. Неизвестные поля верхнего уровня, включая id, status и created_at, запрещены.
- Content-Type — application/json с допустимым charset; лимит тела — 65 536 байт.
- Успех POST после commit: HTTP 201, полный объект уведомления в data, errors=[], Location: /notifications/{id}.
- Ошибка: data=null, errors — непустой массив строк. Оба поля оболочки всегда присутствуют; отдельные error/code/message не вводятся.
- Статусы: 400 — некорректный запрос, 413 — превышение лимита, 415 — Content-Type, 500 — внутренняя ошибка. Не возвращай HTTP 200 для ошибок.
- Неизвестный маршрут — 404; неподдерживаемый метод известного маршрута — 405 с Allow. Ошибки middleware используют общую оболочку.
- Для 500 отдавай только internal server error; SQL, DSN и внутреннюю причину не раскрывай клиенту.

GET /notifications/{id} возвращает HTTP 200 и полный объект уведомления в data. Некорректный UUID даёт 400, отсутствующий — 404, ошибка БД — 500. Чтение выполняется в короткой транзакции без FOR UPDATE и не изменяет запись. pgx.ErrNoRows преобразуется в предметную ошибку отсутствия.

Повторные одинаковые POST создают разные уведомления. При потере ответа после commit повтор может создать дубль; не обещай идемпотентность или exactly-once.

## 5. Правила Go-кода

- Используй gofmt, обычные сокращения ID/HTTP/URL и небольшие функции с ранним возвратом ошибок.
- Передавай context.Context первым аргументом через все слои. Не заменяй контекст запроса фоновым в ходе операции.
- Передавай зависимости через конструкторы; не добавляй глобальное изменяемое состояние приложения.
- Оборачивай ошибки с %w и классифицируй через errors.Is/As, не по тексту.
- Проверяй ошибки Scan, Exec, Commit, закрытия ресурсов; при обходе rows проверяй rows.Err().
- Не используй panic/log.Fatal для штатных ошибок библиотечных слоёв. Точка входа должна завершать процесс с очисткой ресурсов.
- Используй time.Time и TIMESTAMPTZ, отдавай время в UTC, если оно входит в контракт операции.
- Сохраняй точность JSON-чисел; не преобразуй произвольный payload через float64. Учитывай ограничения JSONB при валидации.
- Изменение публичного контракта отражай в спецификации, постановках и тестах.

## 6. PostgreSQL и транзакции

Собственная БД — sharetrip_notification, таблица — notifications.

| Поле | Тип и ограничения |
| --- | --- |
| id | UUID PRIMARY KEY; генерируется приложением |
| recipient_id | TEXT NOT NULL; CHECK на непустое непробельное значение |
| type | TEXT NOT NULL; CHECK на непустое непробельное значение |
| status | TEXT NOT NULL; CHECK на created |
| payload | JSONB NOT NULL DEFAULT '{}'; CHECK на объект |
| created_at | TIMESTAMPTZ NOT NULL DEFAULT now() |

Согласуй определение пробельных строк между доменом и БД. Достаточно индекса первичного ключа; дополнительные таблицы и индексы должны иметь отдельное обоснование. Межсервисные FK и прямой доступ к чужой БД не используются.

- Один pgxpool на процесс: создать, проверить подключение, закрыть при остановке или ошибке инициализации.
- SQL находится в repository; значения передаются параметрами $1, $2 и далее. Перечисляй столбцы явно.
- INSERT RETURNING возвращает фактические значения БД, включая created_at. Ограничения БД дополняют доменные проверки.
- В service реализуй helper begin → операция → commit с отложенным rollback. Это планируемый компонент, а не готовый файл.
- Передавай один pgx.Tx; не используй отдельное соединение для части транзакционной операции.
- Успех возвращай только после успешного commit. Ошибка commit не означает гарантированное отсутствие записи; не запускай слепой повтор.
- Rollback должен иметь отдельный ограниченный контекст очистки. pgx.ErrTxClosed после commit ожидаем; остальные ошибки учитывай, сохраняя исходную причину.
- Для создания одной новой строки FOR UPDATE не нужен. Не выполняй внешние сетевые вызовы внутри транзакции.

## 7. Миграции

- Создавай изменения схемы отдельными файлами migrations/<timestamp>_<action>.sql с уникальным порядком версий.
- Начальная миграция — create_notifications. Up создаёт таблицу и ограничения, Down удаляет таблицу с данными.
- Используй секции Goose Up/Down; StatementBegin/StatementEnd — по необходимости SQL-блока.
- Применённые совместно используемые миграции не переписывай. Для изменения схемы добавляй новую миграцию.
- Миграции запускаются отдельной командой до старта приложения, не из HTTP-обработчика или каждого экземпляра сервиса.
- Проверяй Up на чистой БД; Up → Down → Up — только на одноразовой тестовой БД. Down не восстанавливает удалённые данные.
- Для последующих изменений учитывай совместимость версий приложения, блокировки и миграцию существующих данных.

## 8. Локальная инфраструктура и команды

Целевая конфигурация: приложение на хосте 127.0.0.1:8081, PostgreSQL в Compose с loopback-портом 6544, внутри контейнера 5432. Имя Compose-проекта — sharetrip-notification. Dockerfile приложения не требуется для первой версии.

- Согласуй DB_HOST/PORT/NAME/USER/PASSWORD/SSLMODE, POSTGRES_* и GOOSE_DRIVER/GOOSE_DBSTRING. Обязательны DB_USER и DB_PASSWORD.
- Проверяй конфигурацию до запуска сервера, включая диапазоны портов. Ошибка конфигурации или подключения при старте даёт ненулевой код завершения.
- .env исключён из Git; .env.example содержит описание и несекретные примеры. Не публикуй содержимое .env или раскрытые DSN.
- Compose должен иметь healthcheck и именованный volume. Фиксируй версию образа; не используй latest и фиксированный container_name без необходимости.
- make up ожидает готовности PostgreSQL. make down сохраняет volume; down -v не является обычной остановкой.
- Настройки локального доступа и sslmode=disable не считаются production-конфигурацией.

Планируемые цели Makefile (проверяй наличие перед запуском):

| Команда | Назначение |
| --- | --- |
| make help / deps | Список команд / зависимости и инструменты |
| make tidy / fmt / lint | Зависимости / форматирование / линтеры |
| make test / build / run | Тесты / сборка / локальный запуск |
| make up / down | Запуск / остановка PostgreSQL |
| make migrate-create name=create_notifications | Создание миграции |
| make migrate-status / migrate-up / migrate-down | Статус / применение / откат миграции |

Объявляй цели в .PHONY и help. Инструменты устанавливай в .tools с фиксированными версиями, бинарный файл — bin/notification; поддерживай Windows .exe и Unix-подобные окружения. Согласуй Goose CLI и библиотеку по используемым возможностям.

После реализации последовательность запуска: настроить .env → make deps → make up → make migrate-status → make migrate-up → make run. Запуск Keycloak и другого прикладного сервиса не требуется.

## 9. Логи и жизненный цикл

- JSON-логи в stdout: операция, результат, длительность, request ID и notification ID при наличии.
- Генерируй request ID для запроса, возвращай X-Request-Id и передавай логгер через контекст.
- Не логируй полные payload, пароли и DSN. Внутренние ошибки сохраняй в логах без раскрытия секретов.
- Контекст обращения к БД ограничен таймаутом запроса, по умолчанию 2 секунды. Ошибка таймаута БД даёт 500 по текущему контракту.
- По сигналу прекрати приём новых запросов, предоставь активным до 5 секунд и закрой пул. Фоновые работники в первой версии отсутствуют.

## 10. Тестирование и выполнение задач

- Выполняй постановки с учётом зависимостей в tasks/README.md. Не отмечай проверку выполненной без фактического результата.
- Unit-тестами проверяй конфигурацию и доменные правила. Изменяющие окружение тесты не запускай параллельно.
- SQL, ограничения, JSONB и транзакции проверяй на PostgreSQL 16 через Testcontainers с теми же Goose-миграциями; не заменяй это SQLite или одними моками.
- HTTP-тесты проверяют POST → GET: оба ответа содержат одинаковые данные. Дополнительно проверяй строку БД по id, ошибки GET и сохранность после перезапуска.
- Покрывай корректный POST, отсутствие payload, невалидные поля/JSON, неизвестные поля, лимит тела, Content-Type, ошибки БД, повторные и параллельные POST.
- Проверяй rollback при ошибке после INSERT, ошибку commit без ложного успеха и сохранность после перезапуска. Управляемые подмены допустимы для трудно воспроизводимых сбоев, но не вместо SQL-тестов.
- Изолируй данные UUID; не очищай общие таблицы и не меняй схему одновременно с параллельными тестами.
- Для функционального изменения выполняй форматирование, lint, build и подходящие тесты; финально — make test при доступном Docker.
- Для документации достаточно проверки содержания, локальных ссылок и изменений. Не запускай тесты ради простой правки текста.
- Перед работой проверь состояние репозитория и сохрани чужие изменения. В отчёте укажи результат, реальные проверки и ограничения.
- Поддерживай этот файл в актуальном состоянии: после появления кода обновляй сведения о готовых компонентах, не выдавая планы за реализацию.
